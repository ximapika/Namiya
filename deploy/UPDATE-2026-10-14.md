# 2026-10-14 更新部署与验收

本文对应 [更新任务](../update_doc/2026.10.14_update.md)，说明本次代码的部署准备、迁移、验收和恢复方法。**这些步骤不表示线上已经更新。** 当前校园网 HTTP 入口保持不变，HTTPS 随后续迁移安排。

实际操作顺序是：先执行现有备份服务并确认 `COMPLETE`，再修改配置和准备新密钥；副本演练通过后才进入停机迁移。下文的准备命令均为待执行示例。

## 更新后的行为

- 登录会话同时绑定账号的随机身份标识，删除账号后复用数字 ID 也不能继承旧登录；重置密码会撤销该账号的旧登录。
- 已登录账号默认每分钟 60 次请求，IP 默认每分钟 120 次；登录、验证码、发邮件等入口另有限额。生产继续使用 Redis 共享限流状态。
- 注册、找回密码和绑定邮箱先通过图片验证码，再完成一次性邮箱验证。仅接受 `@pku.edu.cn` 和 `@stu.pku.edu.cn`；每个验证地址最多绑定 3 个账号。
- 每账号每天最多提交 5 次来信或来电，二者合并计数，日期按 `Asia/Shanghai` 划分。
- 列表使用分页、批量关联查询及索引，默认每页 20 条。
- 普通账号连续 90 天没有已登录活动后可被清理；店长、店员始终排除。清理同时删除相关信件、回复、申请和过期验证记录。
- 新注册及重置后的密码使用 scrypt 单向哈希。浏览器使用 RSA-OAEP-SHA256 加密密码提交，挑战绑定浏览器、用途、有效期并只能消费一次；服务端拒绝明文密码表单。
- 数据库只保存邮箱的带密钥摘要及名额编号，不保存可回显的邮箱地址；店长和店员页面不展示邮箱。

## 先准备发信邮箱

需要一个专门用于发送验证码、已开通 SMTP 的邮箱或邮件服务。**发件地址不要求是北大邮箱**；北大邮箱限制针对注册与找回密码的接收地址。可以使用已有专用邮箱，或由运营者开通一个；先确认服务商允许程序发送验证邮件。

在服务商的安全设置中启用 SMTP/客户端访问，生成客户端授权码或应用专用密码，记录以下配置。密码、授权码、完整生产配置不要发送到聊天、截图、日志或 Git；直接在服务器上用受控编辑器配置 `/etc/namiya.env`，保留 `root:namiya 0640` 权限。

| 配置 | 填写内容 |
| --- | --- |
| `MAIL_HOST` | 服务商提供的 SMTP 主机名 |
| `MAIL_PORT` | 对应的加密提交端口 |
| `MAIL_FROM` | 已获授权的发件地址 |
| `MAIL_USERNAME` | SMTP 登录名，通常为完整邮箱地址 |
| `MAIL_PASSWORD` | 客户端授权码或应用专用密码 |
| `MAIL_USE_SSL` / `MAIL_USE_TLS` | 按下面两种方式选择一种 |

常见的 465 端口从连接开始使用 TLS：

```dotenv
MAIL_PORT=465
MAIL_USE_SSL=true
MAIL_USE_TLS=false
```

服务商提供 587 STARTTLS 时：

```dotenv
MAIL_PORT=587
MAIL_USE_SSL=false
MAIL_USE_TLS=true
```

以该服务商实际公布的端口为准。程序验证 TLS 证书；两项加密开关都关闭时拒绝发送，不会退回明文 SMTP。没有配置发信服务时，申请邮箱验证码会失败；应在正式开放新注册和找回密码前完成配置与实邮验收。

若使用北大发件邮箱，可参考学校的 [邮箱客户端及授权密码设置入口](https://its.pku.edu.cn/setting.jsp) 和 [加密端口说明](https://netportal.pku.edu.cn/faq_mail_ssl.jsp)。不同邮箱类型使用不同主机和端口，不能直接把教工邮箱的设置复制给学生邮箱。

## 准备独立密钥，保留原有密钥

`SECRET_KEY` 和 `PHONE_ENCRYPTION_KEY` 必须沿用生产现值。不要用 `.env.example` 覆盖 `/etc/namiya.env`，也不要重新生成旧密钥来“修复”解密错误。

新增 `EMAIL_LOOKUP_KEY`：至少 32 个密码学随机字节，独立于会话、电话加密和 SMTP 密码，并持久保存。它参与邮箱索引，**不能随意轮转**；更换会使原有邮箱匹配、找回密码和名额统计失效。数据库不保存邮箱原文，不能直接靠旧数据库重新生成新摘要。

以下命令仅供部署人员审阅后在服务器执行：它只在该配置项不存在时追加新值，不打印密钥；已有配置（包括空值）需要人工检查，脚本不会覆盖。

```sh
sudo /bin/bash <<'SH'
set -euo pipefail
umask 077
namiya_config=/etc/namiya.env
if grep -Eq '^[[:space:]]*(export[[:space:]]+)?EMAIL_LOOKUP_KEY[[:space:]]*=' "$namiya_config"; then
    printf '%s\n' 'EMAIL_LOOKUP_KEY already exists; keep and inspect the existing setting.' >&2
    exit 1
fi
namiya_lookup_key=$(openssl rand -hex 32)
printf '\nEMAIL_LOOKUP_KEY=%s\n' "$namiya_lookup_key" >> "$namiya_config"
unset namiya_lookup_key
chown root:namiya "$namiya_config"
chmod 0640 "$namiya_config"
SH
```

新增 `PASSWORD_TRANSPORT_PRIVATE_KEY_FILE`：所有 worker 使用同一个 RSA 私钥文件，RSA 至少 3072 位、指数 65537，文件 `0600` 且服务账号可读。生产没有文件时会停止启动，不生成临时私钥，也不允许明文密码降级。

下面使用独占临时文件生成私钥，再通过不覆盖目标的硬链接发布；已存在的私钥保持不变。私钥内容不会打印到终端。

```sh
sudo -u namiya /bin/bash <<'SH'
set -euo pipefail
umask 077
namiya_key=/var/lib/namiya/password-transport.pem
if [ -e "$namiya_key" ] || [ -L "$namiya_key" ]; then
    printf '%s\n' 'Password transport key already exists; keep the existing key.' >&2
    exit 1
fi
namiya_key_temp=$(mktemp /var/lib/namiya/.password-transport.XXXXXXXX)
trap 'rm -f -- "$namiya_key_temp"' EXIT
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 \
    -pkeyopt rsa_keygen_pubexp:65537 -out "$namiya_key_temp"
chmod 0600 "$namiya_key_temp"
ln -T -- "$namiya_key_temp" "$namiya_key"
SH
```

在生产配置中添加绝对路径：

```dotenv
PASSWORD_TRANSPORT_PRIVATE_KEY_FILE=/var/lib/namiya/password-transport.pem
```

开发环境可在 `instance/` 自动生成密钥，测试环境默认使用内存密钥；这些行为不适用于生产。

## 备份、依赖与数据库副本演练

先运行现有备份服务，确认产生含 `COMPLETE` 的备份，再编辑配置、准备新密钥和新的 release。新代码应放入独立的 `/opt/namiya/releases/<release>/`，并预建 `instance/`；不要直接覆盖运行目录，也不要携带开发 `.env` 或数据库。下面变量须替换为实际的新 release 与预演路径。

```sh
sudo systemctl start namiya-backup.service
sudo systemctl status namiya-backup.service --no-pager
namiya_release=/opt/namiya/releases/20261014-update
namiya_preview_venv=/opt/namiya/venv-update-20261014
namiya_preview_db=/var/lib/namiya/migration-preview-20261014.db
```

使用 Python 3.10 或更新版本，在独立虚拟环境中安装 `requirements.lock`；锁文件包括 Pillow 12.3.0 和 Werkzeug 3.1.9。预演时不要修改正在运行服务的虚拟环境。

```sh
sudo /opt/namiya/venv/bin/python -m venv "$namiya_preview_venv"
sudo "$namiya_preview_venv/bin/python" -m pip install -r "$namiya_release/requirements.lock"
```

新配置和私钥就绪后，运行**新 release 中的备份脚本**，以确保新增外部 RSA 私钥也进入快照；旧 release 的备份脚本不具备此能力。脚本仍只依赖系统 Python 标准库。

```sh
sudo /usr/bin/python3 "$namiya_release/deploy/backup.py"
```

从它返回的快照目录中选取含 `COMPLETE` 的备份，将 `worryshop.db` 复制到新建的预演路径，设为 `namiya:namiya 0600`。不要直接复制活跃 SQLite 的主文件：使用备份脚本得到的在线一致性快照，避免遗漏 WAL 数据。

```sh
namiya_snapshot=/var/backups/namiya/daily-REPLACE_WITH_COMPLETED_SNAPSHOT
sudo test -f "$namiya_snapshot/COMPLETE" && \
    sudo test ! -e "$namiya_preview_db" && \
    sudo install -o namiya -g namiya -m 0600 "$namiya_snapshot/worryshop.db" "$namiya_preview_db"
```

若检查失败，先确认快照或重新选择未使用的副本路径；不要继续执行后续迁移命令。

预演命令通过 systemd 加载原配置，再用 `/usr/bin/env` **只覆盖数据库路径**。这样电话解密等仍使用原生产密钥，而写入只落到副本。为使记录数量检查不受可选 bootstrap 影响，预演显式禁用自动创建店长。

```sh
sudo systemd-run --wait --pipe --collect \
    --property=User=namiya --property=Group=namiya \
    --property=WorkingDirectory="$namiya_release" \
    --property=EnvironmentFile=/etc/namiya.env --property=UMask=0077 \
    /usr/bin/env "DATABASE_URL=sqlite:///$namiya_preview_db" BOOTSTRAP_ADMIN_USERNAME= \
    "$namiya_preview_venv/bin/flask" --app run.py init-db
```

在没有其他进程访问副本时再次运行同一命令，验证幂等性。保存检查结果，不将账号、信件、邮箱、电话或密钥内容写入日志：

- 前后用户、信件、回复、申请数量一致，用户 ID、用户名、角色和原密码哈希不变。
- 已加密电话与通话时间仍能用原密钥解密；旧明文字段加密后，解密所得内容与原值一致。
- 新 `auth_id` 非空且唯一；旧账号缺失的活动时间按迁移时刻补齐。第二次迁移不重置这些字段、不重复加密、不新增账号。
- 索引、验证挑战、邮箱名额约束和每日配额表已建立；SQLite `PRAGMA integrity_check` 返回 `ok`。
- 在测试环境验证原有登录、来信、来电、店员审批和店长管理；新注册、验证与找回密码使用合成数据或自己控制的邮箱。

## 维护窗口内正式迁移

副本演练通过后，在维护窗口停止应用，暂停清理任务，另做停机后的最终备份。服务停止期间才升级原生产虚拟环境并迁移正式数据库。

```sh
sudo systemctl stop namiya.service
sudo systemctl stop namiya-cleanup.timer namiya-cleanup.service
sudo /usr/bin/python3 "$namiya_release/deploy/backup.py"
sudo /opt/namiya/venv/bin/python -m pip install -r "$namiya_release/requirements.lock"
sudo systemd-run --wait --pipe --collect \
    --property=User=namiya --property=Group=namiya \
    --property=WorkingDirectory="$namiya_release" \
    --property=EnvironmentFile=/etc/namiya.env --property=UMask=0077 \
    /usr/bin/env BOOTSTRAP_ADMIN_USERNAME= \
    /opt/namiya/venv/bin/flask --app run.py init-db
```

首次部署尚无清理 unit 时，跳过对应 `systemctl stop`。任一步失败都应保持应用停止并检查原因；不要带着迁移失败继续切换。确认正式数据库完整性和数据保持情况后，切换 `/opt/namiya/current` 到新 release，启动 `namiya.service`，检查服务状态、日志和 `/login`。

旧会话不含新的 `auth_id`，更新后要求重新登录是预期行为；不需要因此轮转 `SECRET_KEY`。旧账号保留原密码哈希并可继续验证，迁移不会重置密码或角色。此前没有验证邮箱的账号，必须先用原密码登录，在“验证邮箱”页面绑定后才能使用邮件找回；无法直接靠一个新输入的邮箱找回未绑定的旧账号。

## 启用定期清理

旧账号的空活动时间从迁移时刻起算，得到完整 90 天宽限。之后按已登录活动计时，写入最多每小时刷新一次。清理排除店长和店员；普通账号及关联内容会实际删除，应先保留可恢复备份。

先运行 dry-run；不带 `--apply` 只显示计数，不删除记录。命令仍通过 systemd 取得生产配置：

```sh
sudo systemd-run --wait --pipe --collect \
    --property=User=namiya --property=Group=namiya \
    --property=WorkingDirectory=/opt/namiya/current \
    --property=EnvironmentFile=/etc/namiya.env --property=UMask=0077 \
    /opt/namiya/venv/bin/flask --app run:app cleanup-inactive-accounts \
    --days 90 --batch-size 500
```

确认计数后，手动执行删除时在同一命令最后加 `--apply`。每次最多处理 500 个账号，完成一个批次后退出；大批积压需要多次执行或逐日处理。账号为空时也会有界清理过期挑战记录。

需要每日自动执行时，安装仓库提供的两个 unit，再启用 timer：

```sh
sudo install -o root -g root -m 0644 "$namiya_release/deploy/namiya-cleanup.service" /etc/systemd/system/namiya-cleanup.service
sudo install -o root -g root -m 0644 "$namiya_release/deploy/namiya-cleanup.timer" /etc/systemd/system/namiya-cleanup.timer
sudo systemctl daemon-reload
sudo systemctl enable --now namiya-cleanup.timer
sudo systemctl list-timers namiya-cleanup.timer
```

timer 以**服务器时区**每天 04:30 为基准，额外随机延迟最多 15 分钟；`Persistent=true` 会补跑错过的任务。服务明确使用 `--apply --days 90 --batch-size 500`。检查服务器时区、dry-run 结果和备份后再启用。

## 邮件与功能验收

真实 SMTP 尚未完成验收；隔离测试不会向真实地址发邮件。配置完成后，由运营者用自己控制的北大邮箱完成以下检查：

1. 图片验证码加载、刷新可用，错误或重复使用不会发信；合法验证码可以申请邮件码。检查收件箱与垃圾箱。
2. 完成注册并登录；确认每个验证地址的第 4 个账号被拒绝，其他邮箱域名被拒绝。
3. 旧账号登录绑定邮箱后，用“忘记密码”完成重置；确认旧密码和其他设备的旧会话均失效。
4. 确认浏览器提交只含 `password_challenge` 与 `password_envelope`，不含明文密码；重复提交同一密文失败。
5. 确认普通账号来信与来电合计第 6 次当天提交被拒绝，店员与店长权限、分页和既有信件仍正常。
6. 验证服务启动、Redis 限流、备份 `COMPLETE`、清理 dry-run 与 timer 状态。检查日志不包含邮件地址、验证码、密码或私钥。

## 备份恢复

新版快照包含 `worryshop.db`、`namiya.env`、`release.txt`、`code.tar.gz` 和配置了外部密钥时的 `password-transport.pem`。只有所有步骤成功才写 `COMPLETE`；配置了密钥但文件缺失或不可读取时备份失败。旧配置没有该字段时仍允许生成旧格式快照。

恢复前停止应用和清理 timer，另存当前状态，再选择包含 `COMPLETE` 的一致快照：

- 数据库恢复至 `/var/lib/namiya/worryshop.db`，所有者 `namiya:namiya`、权限 `0600`。确认没有旧实例或遗留 WAL/SHM 文件继续写入该数据库。
- 配置恢复至 `/etc/namiya.env`，所有者 `root:namiya`、权限 `0640`，保留该快照中的 `SECRET_KEY`、`PHONE_ENCRYPTION_KEY` 和 `EMAIL_LOOKUP_KEY`。
- 将 `password-transport.pem` 恢复到备份配置 `PASSWORD_TRANSPORT_PRIVATE_KEY_FILE` 指定的**原绝对路径**，所有者 `namiya:namiya`、权限 `0600`，并保证父目录可由服务账号进入。不要用新生成的文件替换它。
- 恢复对应代码到独立 release，并安装该版本的 `requirements.lock` 后切换链接。数据库、代码与密钥成套恢复；不要仅切回旧代码继续使用已经迁移的新数据库。
- 检查 SQLite 完整性和电话解密，再启动应用。重新核对清理 dry-run，决定何时恢复 timer。

恢复会回退快照之后的数据。同机备份不能覆盖整机丢失，应在后续迁移时安排独立备份。

## 当前安全边界

HTTP 本次按要求延期修改。RSA 仅使密码 POST 不携带明文；公钥和 JavaScript 本身经 HTTP 传输，主动中间人仍可替换它们，会话 Cookie、信件及其他表单字段也没有传输加密。不能把该方案视作 HTTPS 的替代品。后续启用 HTTPS 后再打开 Secure Cookie 与 HSTS。

邮箱 HMAC 降低数据库泄露和管理页面暴露邮箱的风险，但不是“完全匿名”：应用在验证请求中短暂接收邮箱，SMTP 服务商会处理收件地址，持有 `EMAIL_LOOKUP_KEY` 的人能够对候选邮箱做匹配。程序的日志、代理访问日志及错误追踪都应避免收集表单正文。邮箱名额按规范化地址计算；服务商别名指向同一实际邮箱时，本系统没有可靠的别名归并来源，不能宣称所有别名共享 3 个名额。北大对学生邮箱别名的说明见 [官方邮箱服务指南](https://its.pku.edu.cn/about_8.jsp)。

浏览器加密库的固定版本、许可证及上游公告适用范围见 [本地依赖说明](../static/vendor/README.md)。Pillow 固定版本及修复说明见 [12.3.0 官方发行说明](https://pillow.readthedocs.io/en/stable/releasenotes/12.3.0.html)。
